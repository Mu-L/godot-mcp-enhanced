# 2026-07-29 审查修复批次设计（总 spec）

> 承接 2026-07-29 六份审查报告（去重后 ~30 条 finding，已核实 11 条核心全 open，HEAD `e0346a0` / `0.25.0`）。本 spec 定义修复的**批次划分、流程、验收**，不重复各 finding 的细节（细节在报告 + `D:\workspace\Obsidian\GodotMCP\项目待办.md`）。

## 决策（已与用户对齐）

- **范围**：全部去重 finding（~30 条），按优先级 × 维度分 6 批。
- **流程严格度**：每批完整 superpowers SDD（brainstorm → spec → plan → TDD 执行 → final review opus → commit），不论 finding 大小。
- **顺序**：A0（e2e 地基）→ A（安全）→ B（可靠性）→ C（正确性）→ D（addons）→ E（剩余测试）。前批闭环再开下批。

## 顺序决策依据

**A0 提前的硬理由**：A 批次每条修复都要补 `defects.ts` detect 防复发。但若 e2e harness 本身假绿/假红，A 补的所有 detect 地基是虚的——detect 假绿叠加修复假绿（07 月 `2bbdd57`「修 8 个 action 笔误暴露假绿」即此坑）。故 e2e-resilience 是后续每条 TDD 验证的前提条件，而非可排到 E 的「测试类 finding」。它不改生产行为、CI 基建现成、风险最低，是整轮修复最好的热身。

**A 不让路的判断**：A 里无「线上在利用」级 RCE。报告2 headless RCE 链前置 = 2 次 confirm（write_script write risk + create_scene/create_node）+ headless 路径 + AI 被 prompt injection 诱导或恶意 MCP 客户端。本地信任模型下属防御加固级，A0 优先可接受。

**A 不拆（用子序列）的依据**：核实 `src/telemetry/` 路径白名单符号 = 0 匹配 → telemetry 与路径白名单零交集、不经 confirm、是独立 after-hook middleware（ToolDispatcher.ts:466-472），与 RCE 的 profile（executeToolCall:226）同文件不同函数。不拆靠：子序列（telemetry 2 条先行 → RCE 6 条后行）满足「先简单建立节奏」+ 省一次 SDD 周期。注：并非因「共享基建」（实测不共享）。

## 每批流程（完整 SDD）

1. 本总 spec 已定批次总纲；每批进 `writing-plans` 出详细 plan（含 writing-plans 待核实点的代码勘察）
2. TDD 逐条执行：先写失败测试（RED）→ 修到通过（GREEN）；安全/沙箱类须含**反向断言**（isError / deny 路径 / 越界返回）
3. `requesting-code-review`，final review 用 opus
4. 每批多 commit（按 finding 或子序列粒度），master 不 push（[[user-prefers-local-ahead-no-push]]）
5. 前批全部门禁绿 + review 过，再开下批 spec→plan
