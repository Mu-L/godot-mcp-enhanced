# 云路由/多项目管理评估(2026-08-19)

> 待办来源:`D:\workspace\Obsidian\GodotMCP\项目待办.md` 2026-08-19 竞品横扫行动批 [评估] 项。
> 对标:IvanMurzak ai-game.dev(付费 SaaS,云路由/多项目管理为卖点之一)。
> 性质:决策记录,非 spec。结论待商业定位定夺——本文给出推荐与触发条件。

## 结论(TL;DR)

**暂不做云化;多项目管理的本地形态(多实例 registry)已在位,补齐分发叙事即可。**
推荐维持「免费 + 开源 + 本地」定位,云路由留作长期观察项。

## 现状盘点(enhanced 已有的"多项目"基础)

| 能力 | 位置 | 状态 |
|---|---|---|
| 多实例发现/选择 | `godot_list_instances` / `godot_select_instance`(multi_instance 组) | 已发布 |
| 实例 registry 双写 | machine-level(`~/.godot-mcp/instances/`)+ project-level(2026-08-19 反馈批修复端口劫持时升级) | 已发布 |
| bridge 端口解析 | `resolveBridgePort`(registry 心跳条目 → 实际端口,跨项目多 Godot 并行) | 已发布 |
| 转发式多实例 | `instance-http-server.ts`(MULTI_INSTANCE receiver) | 已发布 |

即:**单机多项目并行开发已闭环**——多个 Godot 项目各自起 server/bridge,实例 registry 统一登记,AI 经 list/select 切换。这与 IvanMurzak 云路由解决的"多项目"痛点在本机场景已覆盖;差异仅在**跨机/团队共享**。

## 选项分析

### A. 维持现状(本地多实例)— 推荐

- 与差异化定位一致:「免费 + 开源 + 系统化安全防护」是竞品横扫确认的护城河;云化引入运维面(托管、鉴权、计费、数据合规)直接对撞 SaaS 竞品的主场,以己之短搏彼之长。
- 21 倍 star 差距的根因是分发(AssetLib 长尾流量),不是功能——P0 批(configure/skills)投产比远高于云化。
- 零增量维护成本。

### B. 云路由中心化(instance-http-server 云化)

- 收益:团队共享 AI 侧 Godot 资源池、远程 CI 挂真机 Godot。
- 成本:云基础设施 + 鉴权(现有 bridge 密钥模型是 127.0.0.1 本机信任,上云需重设计)+ 计费/合规;安全面从"本机防误操作"升维到"公网对抗",THREAT_MODEL 需重写。
- 用户需求信号:横扫 22 竞品,云路由仅 ai-game.dev(付费)一家做;开源侧无先例、无 issue 需求。

### C. 折中:多项目管理的本地增强(非云)

- 例:instance registry 的跨项目聚合查询、项目切换的 AI 叙事优化。
- 现有 list/select 已够用;等真实反馈驱动,不预建。

## 触发条件(何时重开评估)

1. GitHub issue / AssetLib 评论出现 ≥3 个独立的跨机协同需求信号;
2. 商业定位变化(若决定做托管服务,本评估作废,另立 spec);
3. 竞品格局变化(开源侧出现云路由先例且获得 traction)。
